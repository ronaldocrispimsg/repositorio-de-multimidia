EVENTOS DO SISTEMA (Exchange Topic: `media.events`)

Lista fechada de eventos (sem curingas):
- `file.uploaded`
- `file.rejected`
- `video.uploaded`, `audio.uploaded`, `image.uploaded`
- `video.processing`, `audio.processing`, `image.processing`
- `video.ready`, `audio.ready`, `image.ready`
- `video.failed`, `audio.failed`, `image.failed`

Filas de trabalho (duráveis):
- `file.uploaded` (binding: `file.uploaded`)
- `video.uploaded` (binding: `video.uploaded` — monitorada pelo KEDA)
- `audio.uploaded` (binding: `audio.uploaded`)
- `image.uploaded` (binding: `image.uploaded`)

Fila de retorno ao backend (`media.backend`, durável):
Recebe exatamente os 10 bindings explícitos (sem wildcard):
- `video.processing`, `audio.processing`, `image.processing`
- `video.ready`, `audio.ready`, `image.ready`
- `video.failed`, `audio.failed`, `image.failed`
- `file.rejected`

Topologia de Retry com Backoff Exponencial (DLX):
- Exchange `media.retry` (topic, durável) -> fila `media.retry.wait` (durável, `x-dead-letter-exchange: media.events`).
- Controle pelo header `x-retry-count` (até 3 tentativas; ao esgotar, publica `video.failed`, `audio.failed` ou `image.failed` e confirma com `ack`).

Payload padrão (snake_case) em todos os eventos:
```json
{
  "event_id": "uuid-v4",
  "file_id": "uuid-v4",
  "type": "video | audio | image",
  "filename": "nome_sanitizado.mp4",
  "storage_key": "raw/<file_id>/original",
  "mime_type": "video/mp4",
  "original_size": 1048576,
  "occurred_at": "2026-11-02T22:00:00.000Z",
  "status": "uploaded | processing | ready | failed | rejected",
  "result": {
    "url": "/streams/<file_id>/playlist.m3u8",
    "size": 980000,
    "format": "hls"
  },
  "error": null
}
```
